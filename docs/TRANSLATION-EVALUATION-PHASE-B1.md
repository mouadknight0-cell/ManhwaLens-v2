# Phase B1 — preparing the real-device baseline evaluation

Continues from Phase A (`cb3a67a`). This phase builds the *workflow* for
collecting real device translations and human-reviewed Arabic references. It does
**not** improve translation quality and makes **no quality claim**.

## 3. How to review the 40 Arabic references

```
python3 -m scripts.translation_eval review-sheet
```

Writes `evaluation/review/review-sheet.html`. It is one self-contained file: no
CDN, no `fetch`, no external stylesheet (asserted by test). Open it by
double-clicking, or copy it to the phone and open it in any browser.

For each case it shows the id, the English source, the current Arabic in a
**right-to-left editable box**, the reviewer-only context, and a decision
selector. You can edit the Arabic to correct it before approving.

Rules the tool enforces:

- **Nothing is approved by itself.** A case you leave alone stays
  `pending_human_review`; the page only emits cases you actually decided.
- **Your name is required** — decisions must be attributable.
- **No timestamp is generated by the page.** It emits no time field at all; the
  import step records the moment you saved.
- **`disputed`/`rejected` require notes**, and both **keep the reference text** —
  a disagreement is recorded, not deleted.
- Saving downloads `review-decisions.json`. If Android blocks the download, the
  JSON is shown in a box to copy manually.

Then apply them:

```
python3 -m scripts.translation_eval apply-review --decisions review-decisions.json
```

This refuses to write a corpus that fails schema validation, skips
already-reviewed cases unless you pass `--allow-override`, and never upgrades a
case you did not name.

## 4. How to collect real translations on your phone

Two routes, both genuine device execution.

### Route A — CI emulator (no phone needed, but not your device)

`android-quality.sh` already runs `./gradlew connectedDebugAndroidTest` and pulls
`overlay-evidence`. The new test exports
`overlay-evidence/translation-eval-export.json` and CI uploads it as the
`android-quality-results` artifact. This gives real ML Kit output from an
emulator, clearly labelled `"emulator": true` in the export.

### Route B — your Xiaomi (the authoritative one)

```
# 1. Build and install the debug app + test APK
./gradlew installDebug installDebugAndroidTest

# 2. Run only the export test, tagging the commit
adb shell am instrument -w \
  -e class com.manhwalens.app.TranslationEvalExportTest \
  -e gitRevision "$(git rev-parse HEAD)" \
  com.manhwalens.app.test/androidx.test.runner.AndroidJUnitRunner

# 3. Pull the export
adb pull /sdcard/Android/data/com.manhwalens.app/files/overlay-evidence/translation-eval-export.json .
```

Notes that matter:

- The app must already have the EN→AR model installed (open the app once and let
  it download, on any network). After that the run is fully offline — you can
  switch to airplane mode first, and the export will show what actually happened.
- The test calls the **same** `TranslationClient.translateBlock` the reader uses,
  with a reliable region, confidence 1.0 and no retry overrides — the conditions
  the Phase 3 benchmark procedure specifies.
- `gitRevision` is passed in because the app cannot read its own commit. If you
  omit it the importer flags the run as **not usable as a reproducible baseline**
  rather than silently accepting it.
- A failure is a result: timeouts and empty outputs are exported, not skipped.

Without a phone, Route A is available but is emulator evidence, and the report
says so. **No claim of phone execution is made anywhere in this phase.**

## 5. How to export the device outputs

The export is a single JSON file at
`/sdcard/Android/data/com.manhwalens.app/files/overlay-evidence/translation-eval-export.json`
(CI artifact: `android-quality-results`). Per case it records `case_id`,
`status`, `translated`, `error_code`, `method`, `duration_ms`; and once per run
`engine_id`, `revision`, `app_version`, `model_identity`, and device
manufacturer/model/SDK/ABI/emulator flag.

**The Arabic reference is never present in this file or in the device asset** —
asserted by test. Only ids and English are shipped to the device.

## 6. How to import into the harness

```
python3 -m scripts.translation_eval import-device \
  --export translation-eval-export.json \
  --out evaluation/device/baseline-outputs.json

python3 -m scripts.translation_eval evaluate \
  --baseline  evaluation/device/baseline-outputs.json \
  --candidate evaluation/device/baseline-outputs.json \
  --out evaluation/reports
```

(Once a candidate engine exists, point `--candidate` at its export.)

`import-device` exits 0 on a complete run, 1 when cases are missing or the
revision is unknown, and 2 on a malformed file. Failures keep their `failed`
status with the error code; missing cases become `missing` in the harness and are
counted in Report B — never back-filled.

## 7. Tests and actual results

| Suite | Result |
| --- | --- |
| Phase B1 tests (`test_translation_eval_phase_b1.py`) | **54 passed** |
| Whole Python suite | **189 passed**, 0 failures |

Verified end to end with a simulated round trip (clearly labelled as simulated):

- 3 reviewed + 1 disputed → corpus shows `reviewed: 3, disputed: 1,
  pending_human_review: 36`; untouched cases stay pending; fingerprint changes.
- 40-case device export with 4 timeouts and 2 empty outputs → all 40 imported,
  `{ok: 34, failed: 4, empty: 2}` preserved.
- Evaluate on that corpus → 40 rows, `baseline missing 0`, 3 references valid for
  scoring, 36 pending, `semantic_quality_score: null`, exit 1.

### 7.1 Phase A tests changed

Two Phase A safety tests were updated, and this is disclosed rather than glossed:

- `test_imports_stay_within_stdlib_and_the_package` — allowlist gained `datetime`
  and `html`. Both are standard library with no network or inference capability;
  every banned networking module remains banned.
- `test_no_stash_foreign_changes_are_in_the_working_tree` — the worktree
  allowlist gained this phase's own paths.

No assertion was weakened or deleted. `schema.py` and `harness.py` were not
modified at all.

### 7.2 Not run here

- **No JDK / Android SDK / emulator in this environment.** The Kotlin export test
  was therefore **not compiled or executed locally**. Its Android-side correctness
  is verified only by CI. The Python halves are fully tested here.
- No real device translation was produced in this phase. No output in this
  repository is presented as a genuine ML Kit translation.

## 8. What remains manual

1. **Reviewing the 40 references.** Requires a bilingual human; the tool collects
   and enforces but cannot judge.
2. **Running on your Xiaomi.** Route B above.
3. **Deciding `disputed` cases** — the harness records them and excludes them from
   scoring; someone must adjudicate.
4. **Length and semantic-category classification** of the 40 stays unset; the
   Phase A matrix reports those as gaps.
5. **Corrupted-OCR cases** do not exist and must not be invented; the OCR strata
   gap remains.

## 9. Blockers

- **Nothing in this phase is blocked.** The workflow is complete and tested.
- **Producing the first real baseline report is blocked on you**, on two inputs
  that only you can supply: (a) a device export from Route A or B, and (b) at
  least some references genuinely reviewed. With both, `evaluate` produces
  Report B immediately.
- Until then the harness correctly reports `semantic_quality_score: null` and
  exits 1, which is the intended signal that the data is incomplete — not a
  defect.
